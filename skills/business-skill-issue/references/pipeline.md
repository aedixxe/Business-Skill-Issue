# Локальная страница проекта

Страница показывает карту этапов, текущее положение и историю работы: материалы, вопросы с ответами, документы, согласования, дизайн, реализацию и приёмку. Она открывается как обычный локальный HTML. Данные проекта не требуется публиковать или передавать внешнему сервису.

## Создание и обновление

Храни `pipeline.json` рядом с материалами проекта; HTML — его производный результат. Используй комплектный `examples/demo-pipeline.json` как пример формата, если он нужен; синтетическое содержание замени сведениями своего проекта. Не копируй демонстрационную историю в реальный проект и не отмечай ещё не выполненные этапы завершёнными.

Запускай из папки установленного скилла, подставив реальные пути проекта:

```bash
python3 scripts/render_pipeline.py --input <папка-проекта>/pipeline.json --output <папка-проекта>/pipeline.html
```

Нужен Python 3 и только стандартная библиотека; сетевые запросы и CDN не используются. HTML можно открыть в доступном локальном просмотрщике или браузере. Рендеринг не отправляет документы и не меняет их согласование. Если Python недоступен, сохрани JSON и документы, сообщи, что страница ещё не пересобрана; продолжай содержательную работу без установки зависимостей по собственной инициативе.

После существенного **сохранённого** обновления — материалов, ответов, правил, версии, блокера, согласования или результата проверки — обнови JSON и пересобери страницу. Не делай рендеринг каждого сообщения обязательным. Сначала сохраняй канонические материалы, затем проекцию и HTML. При ошибке рендера исходные сведения остаются сохранёнными, а HTML может быть устаревшим: сообщи об этом точно.

## Контракт `schema_version: 1`

Корневой объект:

| Поле | Содержание |
|---|---|
| `schema_version` | Число `1` |
| `project` | `{name, description?, current_version_id?}`; название обязательно, текущую версию указывай явно, когда она есть |
| `updated_at` | Известная дата/время последнего обновления проекции |
| `current` | `{stage_id?, summary?, blockers: [], next_step?}`; сводка и рекомендуемое действие |
| `stages` | Массив этапов в порядке карты |
| `events` | Журнал событий с устойчивыми ID |
| `versions` | Ссылки на закреплённые версии документов или результатов |
| `approvals` | Решения о согласовании точной версии и объёма |

Массивы присутствуют даже когда пусты. Символ `?` в этом описании означает необязательное поле, он не является частью имени JSON-ключа. Сами требования и полные документы остаются в канонических материалах; не дублируй их отдельным независимо редактируемым реестром в JSON.

### Этапы

`{id, title, status, needed_step?, skip_reason?, blockers?}`

- `pending` — ещё не начат;
- `in_progress` — выполняется;
- `blocked` — продолжению мешает указанная причина;
- `done` — результат этапа получен в обозначенном объёме;
- `skipped` — неприменим, обязательно заполнить `skip_reason`.

`needed_step` — строка с действием, `blockers` — массив строк. ID выбирай один раз, например `task`, `materials`, `process`, `requirements`, `approval`, `specification`, `delivery`, `acceptance`. Можно адаптировать карту к проекту и вести несколько этапов одновременно. Завершение написания документа не завершает его согласование. После изменения открывай затронутый этап снова и добавляй событие с причиной.

### События

`{id, title, type?, stage_id?, occurred_at?, recorded_at?, summary?, details?, version_id?, questions?, artifacts?, corrects_event_id?}`

`id` и `title` обязательны. Типы: `intake`, `questions`, `answers`, `document`, `approval`, `design`, `build`, `acceptance`, `change`, `correction`, `general`. `summary` — короткая строка; `details` — более подробный текст. Связанные файлы лежат в `artifacts`, а раскрываемый список вопросов — в `questions`.

`occurred_at` — когда произошло событие; `recorded_at` — когда оно записано. Используй ISO-дату `YYYY-MM-DD` или ISO-дату/время с часовым поясом, если известны. Неизвестное оставь `null` или пропусти. Неточная фраза «в начале месяца» остаётся в тексте, не превращается в выдуманный день. Поздний ответ записывается сейчас с его известной датой получения, исходный вопрос остаётся на прежнем месте.

История читается по дате события сверху вниз, от ранних к поздним; при одинаковой дате сохраняется порядок записей в JSON. События с неизвестной датой показываются отдельно по известной дате записи, без подмены одной даты другой.

Вопрос в карточке:

```json
{
  "id": "Q-001",
  "text": "Что происходит с заявкой после отказа?",
  "status": "partial",
  "answers": [
    {
      "text": "Инициатор получает уведомление. Повторную подачу ещё обсуждаем.",
      "occurred_at": null,
      "recorded_at": "2026-01-15T12:00:00Z",
      "source": "Поступление ответов A-001, вопрос Q-001"
    }
  ]
}
```

`status` вопроса: `open`, `partial`, `answered`; дополнительные состояния канонического реестра, например перенос вопроса, объясняй в `details` события. `source` — строка, объясняющая происхождение; ссылку на сохранённый ответ добавь в `artifacts` события. Сохраняй исходный вопрос вместе с ответом, чтобы карточка читалась без догадок. Позднее поступление получает новое событие, связанное тем же Q-ID. Это отображение канонической записи вопроса и ответов, а не альтернативная редакция.

Исправляющее событие имеет `type: "correction"` и `corrects_event_id`. Объясни ошибку и верное содержание; не удаляй первоначальное событие и не делай вид, что новый ответ был известен раньше.

### Артефакты и версии

Артефакт: `{label, path?, url?, version_id?}`. Укажи понятную подпись и один адрес: относительный `path` внутри папки с `pipeline.json` либо разрешённый `url` (`http`, `https`, `mailto`). Ссылки на внешний ресурс добавляй лишь когда он уже относится к проекту. Локальные пути не должны выходить из папки проекта; абсолютные пути и обход через `..` не используются. Для явно перечисленных локальных `.md` и `.txt` renderer встраивает безопасный текстовый просмотр с лимитом 256 КиБ на файл; другие форматы остаются ссылками. Содержимое внешних ссылок не загружается. HTML с текстовыми просмотрами содержит эти материалы: считай его частью проекта, а не обезличенной оболочкой.

Версия: `{id, label, created_at?, scope?, kind?, artifacts: []}`. Укажи неизменяемый снимок и его объём, например `scope: "Первичная подача и отказ; без повторной подачи"`. `kind` можно использовать для требований, ТЗ, макетов или результата сборки. Дата неизвестна — оставь её неизвестной. `project.current_version_id` ссылается на существующую версию, чью актуальную готовность и согласование рассматриваем.

### Согласования

`{id, version_id, scope, decision, decided_at?, actor?, evidence: [], note?}`

Обязательны ID решения, существующая версия, точный непустой объём, решение и массив свидетельств. `decision`: `requested`, `approved`, `rejected`, `changes_requested`. `evidence` — артефакты того же формата с сохранённым подтверждением или ссылкой на конкретное сообщение/версию. `actor` указывай только когда известен; не придумывай согласующего.

Для `approved` требуется свидетельство явного подтверждения. Согласование текущей версии показывается применимым лишь при совпадении `version_id` с `project.current_version_id`, совпадении `scope` с объёмом этой версии и наличии доступной ссылки в `evidence`. Итог учитывает последнее решение по дате; если у относящегося к версии решения дата неизвестна и порядок нельзя определить, страница показывает неясный статус. Дату ради зелёного статуса не выдумывай. Приложенный файл сам по себе не является согласием: перед записью статуса проверь содержание и полномочие подтверждающего по [readiness.md](readiness.md). Renderer проверяет структуру и связи, а не смысл свидетельства.

Если согласована только часть, зарегистрируй точную версию этого ограниченного объёма и ссылайся на неё; не распространяй согласие на весь проект. Исторические решения остаются видимыми после смены текущей версии. Решение хранится в `approvals`, событие `approval` показывает его в истории со ссылкой на ту же версию и доказательства. Не поддерживай два разных решения в этих записях.

Готовность реализации и технические блокеры показывай отдельно в сводке, этапах и связанном заключении. JSON не заменяет содержательную проверку готовности и не делает историческое согласование действующим для новой версии.
